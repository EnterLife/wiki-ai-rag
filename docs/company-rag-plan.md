# План внедрения RAG в компании

## Текущее состояние проекта

Технический фундамент готов для пилота: изоляция пользователей и источников,
OIDC/JWKS, ACL по группам, PostgreSQL для служебных данных, Qdrant, фоновые задания,
инкрементальная индексация, гибридный поиск, reranker, строгая проверка цитат,
безопасный отказ и production Compose.

Принцип ответа системы:

```text
Нет достаточного источника — нет ответа.
```

Готовность к production теперь зависит главным образом не от добавления ещё одного
LLM, а от корпоративных источников, прав доступа, эталонного набора вопросов,
инфраструктуры, владельцев данных и эксплуатационных процедур.

## Рекомендуемый порядок работ

### 1. Определить владельца и границы пилота

- Назначить владельца продукта, владельца каждого источника и ответственного за ИБ.
- Выбрать один подразделение и 2–3 сценария с измеримой пользой.
- Зафиксировать, какие вопросы система не должна обслуживать.
- Определить срок актуальности, классификацию и правила удаления данных.

Результат: согласованный паспорт пилота и список допустимых источников.

### 2. Подготовить эталон качества

- Собрать реальные вопросы пользователей, включая неоднозначные и провокационные.
- Для каждого вопроса указать ожидаемые документы или отметить, что ответа нет.
- Добавить вопросы с устаревшей информацией и из недоступных пользователю разделов.
- Разделить набор на настройку и независимую приёмку.

Результат: versioned evaluation dataset, который не меняют ради улучшения метрик.

### 3. Подключить корпоративную идентификацию

- Зарегистрировать SPA и API в корпоративном OIDC-провайдере.
- Сопоставить группы IdP с `access_groups` источников.
- Создать отдельную административную группу.
- Проверить запрет поиска, цитирования и прямого чтения chunks другой группы.

Результат: один и тот же пользователь имеет одинаковые права в UI, API и retrieval.

### 4. Инвентаризировать и очистить источники

- Удалить дубли, черновики, просроченные документы и секреты.
- Сохранить заголовок, раздел, страницу, URL, дату обновления и стабильный ID.
- Назначить freshness SLA и расписание индексации.
- Начать с небольшого числа качественных источников, а не со всего файлового хранилища.

Результат: реестр источников с владельцем, группами, SLA и правилами хранения.

### 5. Настроить ingestion и безопасную переиндексацию

- Запустить PostgreSQL, Redis/Celery и Qdrant.
- Создавать credentials через secret manager, не через frontend или Git.
- Для каждой схемы документа проверить parsing, chunk metadata и ссылку цитаты.
- Использовать incremental jobs для обычных обновлений.
- При смене embedding-модели строить новую коллекцию и переключать Qdrant alias только
  после приёмки.

Результат: повторяемая индексация, сохраняющая предыдущие chunks проблемного документа.

### 6. Настроить retrieval по измерениям

- Сначала измерить dense + BM25/RRF без генерации.
- Подобрать `top_k`, веса и пороги на эталонном наборе.
- Добавить reranker только если он улучшает независимый набор.
- Проверять качество отдельно по языкам, подразделениям и типам источников.

Результат: зафиксированная конфигурация с воспроизводимыми retrieval-метриками.

### 7. Подключить LLM и проверить grounded-ответ

- Использовать structured output с claims и citation IDs.
- Отбрасывать ответ целиком при неизвестной, отсутствующей или неверной цитате.
- Не передавать в prompt credentials и лишние персональные данные.
- Проверить prompt injection как в вопросе, так и внутри индексируемого документа.

Результат: каждое важное утверждение подтверждено разрешённым источником.

### 8. Провести эксплуатационную приёмку

- Проверить backup/restore PostgreSQL и Qdrant на чистом окружении.
- Настроить TLS, сетевые политики, централизованные логи и алерты.
- Нагрузочно проверить indexing и p95 latency `/ask`.
- Провести security review, red-team и проверку утечек между ACL-группами.

Результат: подписанные протоколы качества, ИБ и восстановления.

### 9. Запустить ограниченный пилот

- Начать с небольшой группы пользователей.
- Еженедельно разбирать отказы, слабые retrieval results и неверные цитаты.
- Исправлять прежде всего данные и retrieval, а не prompt.
- Расширять охват только после прохождения согласованных порогов.

## Рекомендуемые критерии приёмки

Конкретные значения задаются владельцами продукта и ИБ. Минимальный набор измерений:

- Recall@K / nDCG retrieval на эталонных документах.
- Доля важных утверждений с валидной цитатой.
- Точность отказа на вопросах без ответа.
- Число ACL-утечек: всегда `0`.
- Доля документов, проиндексированных в пределах freshness SLA.
- p95 latency, error rate и стоимость одного ответа.
- Успешное восстановление из backup в заданный RTO/RPO.

## Что требуется от компании

| Область | Что предоставить |
| --- | --- |
| Сценарии | 2–3 приоритетных use case и владельца продукта |
| Данные | источники, владельцев, классификацию, SLA и правила удаления |
| Качество | реальные вопросы и ожидаемые документы/отказы |
| Доступ | OIDC issuer, audience, JWKS URL, client ID и группы |
| Инфраструктура | домены, TLS, PostgreSQL, Redis, Qdrant, backup и monitoring |
| Модели | разрешённые embedding/LLM/reranker endpoints и лимиты |
| Безопасность | secret manager, сетевые правила, аудит и процесс инцидентов |
| Эксплуатация | SLO, RTO/RPO, бюджет, поддержка и владелец on-call |

## Что осталось после технического этапа

Приоритет P0 перед production:

- заполнить production secrets и OIDC-параметры;
- подключить реальные источники и утвердить их ACL;
- подготовить независимый evaluation dataset;
- прогнать PostgreSQL/Qdrant integration и backup/restore в целевом окружении;
- провести нагрузочную и security-проверку.

Приоритет P1 после пилота:

- сохранять историю evaluation runs и показать её в admin UI;
- добавить нужные компании коннекторы;
- при большом корпусе заменить прикладной BM25 scan на native sparse index;
- настроить корпоративные dashboards, алерты и cost accounting.
